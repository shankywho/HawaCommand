# Phase 3: Database & PostGIS Data Models

> **Status (2026-10-10).** Partial: 23 SQLAlchemy tables, tested on SQLite. There are no Alembic migrations, no PostGIS geometry columns, and the API never opens a session. Overview: [backend/README.md](../README.md#implementation-status).


## Overview
Phase 3 establishes the database layer of the HawaCommand backend using SQLAlchemy 2.0. It defines the tables for spatial administrative boundaries, 500 m computational cells, registered IoT sensors, calibrated readings, fleet assets, daily dispatch plans, verified interventions, and audit outboxes.

## Artifacts & Components Created

1. **`hawa_backend.db.base`** (`src/hawa_backend/db/base.py`):
   - `DeclarativeBase` with naming conventions for indexes, constraints, and foreign keys.
   - `TimestampMixin`: Automatically maintains `created_at` and `updated_at` with UTC timestamps.
   - `SimulatedMixin`: Enforces the honesty rule by tagging rows with `is_simulated: bool` (indexed).

2. **`hawa_backend.db.session`** (`src/hawa_backend/db/session.py`):
   - Async engine and session factory (`create_async_engine`, `async_sessionmaker`).
   - Supports production PostgreSQL 16 + PostGIS via `asyncpg` and isolated unit testing via `aiosqlite`.
   - `get_db()` async generator dependency for FastAPI route handlers with automatic commit and rollback on failure.

3. **Domain Models** (`src/hawa_backend/db/models/`):
   - **`grid.py`**:
     - `Ward`: MCD administrative wards with centroid coordinates and population.
     - `Cell500m`: 500 m digital twin computational cells with parent 1 km cell IDs and key cell pre-rankings.
     - `School`: Monitored school locations with daily morning assembly times.
     - `Site`: Construction and industrial sites with dynamic compliance grading (`A`, `B`, `C`).
     - `ReferenceStation`: Regulatory monitoring stations (CPCB / DPCC / OpenAQ).
   - **`device.py`**:
     - `Device`: Hardware registry (`HPM-*`, `HPS-*`, `HTG-*`, `HEY-*`) with placement, trust scores, and active calibration version.
     - `Reading`: Hourly and continuous calibrated particulate observations with spatial cell indices.
     - `DeviceEvent`: Rapid hardware spike detections, tamper alerts, and device telemetry.
   - **`asset.py`**:
     - `Asset`: Municipal anti-pollution fleet (water sprinklers, anti-smog guns, sweepers, inspection teams) with water tank capacities and attached HawaTag IDs.
     - `AssetShift`: Driver assignments with active shift time windows.
   - **`plan.py`**:
     - `Plan`: Ward-level daily master plans or reactive spike plans with window labels and review status (`drafting`, `draft`, `approved`, `done`).
     - `PlanTask`: Ordered route stops, operations (`add`/`del` vs standard route), and cause rationales.
     - `PlanReview`: Agent critiques and audit objections generated by the Planner and Auditor LLM agents.
   - **`intervention.py`**:
     - `Intervention`: Logged spray sessions with telemetry (litres delivered, flow rate, ambient PM before/after).
     - `Impact`: Synthetic-control verified effect percentages with 95% confidence intervals and p-values.
     - `EffectivenessLibrary`: Learned empirical efficacy distributions per cause and asset type.
   - **`alert.py`**:
     - `Alert`: Bilingual (English and Hindi) alerts for schools, outdoor workers, and citizens.
     - `AlertDelivery`: Multi-channel dispatch tracking across WhatsApp, SMS, and FCM push.
   - **`auth.py`**:
     - `AppUser`: User accounts with role-based access control and ward boundaries.
     - `RefreshToken`: Cryptographically hashed session tokens.
     - `AuditLog`: Immutable audit trail for compliance and officer actions.
   - **`outbox.py`**:
     - `OutboxEvent`: Transactional outbox ensuring reliable event publication to Kafka without distributed transactions.
     - `ProcessedEvent`: Consumer deduplication table preventing duplicate event execution.

## Testing & Verification
All unit tests in `tests/db/test_db.py` were executed against an in-memory async SQLite engine:
```bash
PYTHONPATH=src:contracts .venv/bin/pytest tests/db
# 4 passed in 0.49s (100% pass)
```

Verified test cases include:
- Foreign key linking between `Ward` and `Cell500m`.
- Calibrated `Reading` insertion and honesty rule `is_simulated` indexing.
- End-to-end plan dispatch flow: `Asset` $\to$ `Plan` $\to$ `PlanTask` $\to$ `Intervention` $\to$ `Impact`.
- Transactional `OutboxEvent` creation and status filtering.
